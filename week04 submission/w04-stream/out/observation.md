# Week 4 · Mining Data Streams — 관찰 노트

## Task 1 · 세 가지 스케치

Bloom filter가 거짓 음성을 못 내는 건 구조상 당연하다. 아이템을 넣을 때 해당 비트들을 1로 켜기만 하고 끄는 적이 없으니까, 넣은 적 있는 아이템을 조회하면 그 비트들은 반드시 아직 1이고, 그래서 "없다"가 나올 수가 없다. 예측 FP율은 §4.4.2의 (1 - e^(-kn/m))^k로 계산했고(m=8192, k=5, n=800 → 0.86%), 실측은 0.905%로 꽤 잘 맞았다. 살짝 차이 나는 건 이중 해싱으로 만든 k개 인덱스가 완전히 독립적이진 않고 표본도 유한해서 생기는 정상 오차라고 본다.

Flajolet-Martin 결합은 §4.5.3의 확률적 평균화(그룹화)를 썼다. 아이템마다 해시 하나로 레지스터(그룹)를 고르고 각 레지스터의 최대 후행 0 개수를 유지한 다음, 지수를 먼저 평균내고(2^R의 기하평균이라 지수적 분산을 눌러준다) 보정 상수로 중심을 맞췄다. 처음엔 2^R를 직접 평균내 봤는데 운 좋은 레지스터 하나가 값을 지배해서 크게 튀었고, 중앙값은 견고하긴 한데 2의 거듭제곱으로만 나와서 해상도가 나빴다. 최종 추정은 참값의 1.16배쯤이라 2배 이내에 안정적으로 들어온다.

Reservoir sampling은 k개만 들고도 균등하다. 처음 k개를 담고, i번째(0-기준) 아이템은 randint(0,i)가 k 미만일 때만 교체한다. 스트림 길이 n을 미리 안 알아도 되는 지점이 딱 이 한 줄이다. 각 단계에서 교체 확률을 k/(i+1)로 두면, 길이를 끝까지 몰라도 최종적으로 모든 아이템이 정확히 k/n 확률을 갖게 된다.

## Task 2 · Exact가 안 되는 크기 (내 기계 측정)

측정 기계는 Windows 11 · Intel Family 6 Model 142 · Python 3.13.2다. 정확 set은 2500만(25M)에서 불쾌해졌다. 한 번에 131초(2분 넘게) 걸렸고, 여기선 시간이 먼저 바닥났다. 메모리도 745 MB까지 올라서 고유값에 비례해 계속 올라가는 중이라(선형), 시간 뒤를 메모리가 바짝 쫓는 모양이었다.

A4 두 성장률: 정확 set 메모리는 데이터 4배마다 약 4배로 커져서(3.9 → 11.6 → 46.6 → 188.3 → 744.7 MB) 고유값에 비례하는 O(n) 선형이고, FM 메모리는 10만 → 2500만(250배)으로 늘려도 4,396 → 4,400 바이트라 사실상 O(1) 상수다(크기를 정하는 건 레지스터 64개뿐이다). 정확도 비율은 1.43·1.57·1.11·0.93·1.02로 n이랑 상관없이 배회한다.

"오늘 방문한 고유 사용자 수"에 2배 오차가 괜찮냐를 생각해 보면, 괜찮은 경우는 대충 용량 잡거나 추세·이상 탐지("트래픽이 대충 두 배 됐네")처럼 자릿수만 맞으면 되는 대시보드다. 안 되는 경우는 고유 사용자당 과금, 정확한 광고 도달 수 보고, SLA/쿼터 판정처럼 150만이냐 230만이냐가 결정을 바꾸는 데다. 여기선 2배 오차가 그대로 돈이나 계약 오류가 되니까 쓰면 안 된다.

## Task 3 · 같은 메모리, 더 적은 실수

바꾼 파라미터는 해시 개수 k다. §4.4.2의 FP율 (1 - e^(-kn/m))^k를 k로 미분해서 0으로 두면 최소가 k* = (m/n)·ln2에서 나온다. 이 과제는 m=80,000 bits, n=8,000 items라 m/n=10이 고정이고, 그래서 k* = 10·ln2 = 6.93 → k=7이다. Naive는 k=1이라 비트를 낭비했는데, k=7로 바꾸니 FP율이 9.511% → 0.831% (91.3% 감소), 거짓 음성 0, 예산 내(80,000 bits)로 들어왔다.

R6 — 10 bits/item의 이론 바닥은 k=7일 때 (1 - e^(-0.7))^7 ≈ 0.82%인데, 실측 0.831%라 거의 바닥에 닿았다(약 0.01%p 차이는 유한 표본 오차).

n을 모를 때가 문제인데, 너무 낮게 잡으면 실제 아이템이 예상보다 많이 들어와서 비트가 포화되고 FP율이 확 치솟는다(최악엔 거의 모든 조회가 "yes"). 너무 높게 잡으면 k가 과해지거나 비트당 아이템이 적어져서 메모리를 낭비한다. 실무 해법은 확장형(scalable) Bloom filter(채워지면 새 필터를 이어 붙여서 목표 FP율을 유지)나, 삭제까지 되는 Cuckoo filter를 쓰는 거다.
