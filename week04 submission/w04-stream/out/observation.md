# Week 4 · Mining Data Streams — 관찰 노트

## Task 1 · 세 가지 스케치

Bloom filter가 거짓 음성을 낼 수 없는 이유는 구조적이다 — 아이템을 넣을 때 해당 비트들을 1로 켜기만 하고 절대 끄지 않으므로, 넣은 적 있는 아이템을 조회하면 그 비트들은 반드시 여전히 1이어서 "없다"가 나올 수 없다. 예측 FP율은 §4.4.2의 `(1 - e^(-kn/m))^k`로 계산했고(m=8192, k=5, n=800 → 0.86%), 실측은 0.905%로 잘 맞았다. 근소한 차이는 이중 해싱으로 만든 k개 인덱스가 완전히 독립적이지 않고 유한 표본이라 생기는 정상 오차다.

Flajolet-Martin 결합 규칙은 §4.5.3의 **확률적 평균화(그룹화)**를 썼다: 아이템당 해시 하나로 레지스터(그룹)를 고르고 각 레지스터의 최대 후행 0 개수를 유지한 뒤, 지수를 먼저 평균내고(2^R의 기하평균 → 지수적 분산을 억제) 보정 상수로 중심을 맞췄다. `2^R`를 직접 평균내는 방법은 운 좋은 한 레지스터가 값을 지배해 크게 튀었고, 중앙값은 견고하지만 2의 거듭제곱으로만 나와 해상도가 나빴다. 최종 추정은 참값의 약 1.16배로 2배 이내에 안정적으로 들어온다.

Reservoir sampling은 k개만 들고도 균등하다: 처음 k개를 담고, i번째(0-기준) 아이템은 `randint(0,i)`가 k 미만일 때만 교체한다. 스트림 길이 n을 **미리 알 필요가 없는 지점**이 바로 이 한 줄 — 각 단계에서 교체 확률을 `k/(i+1)`로 두면, 길이를 끝까지 몰라도 최종적으로 모든 아이템이 정확히 `k/n` 확률을 갖게 된다.

## Task 2 · Exact가 안 되는 크기 (내 기계 측정)

측정 기계는 Windows 11 · Intel Family 6 Model 142 · Python 3.13.2다. 정확 set은 **2500만(25M)에서 불쾌해졌다** — 한 번에 131초(2분 이상)가 걸렸고, 이때 **시간이 먼저** 바닥났다. 메모리도 745 MB까지 올라 고유값에 비례해 계속 상승 중이라(선형), 시간 뒤를 메모리가 바짝 쫓는 형태였다.

A4 두 성장률: 정확 set 메모리는 데이터 4배마다 약 4배로 커져(3.9 → 11.6 → 46.6 → 188.3 → 744.7 MB) **고유값에 비례하는 O(n) 선형**이고, FM 메모리는 10만 → 2500만(250배)에도 4,396 → 4,400 바이트로 **사실상 O(1) 상수**다(크기를 정하는 건 레지스터 64개뿐). 정확도 비율은 1.43·1.57·1.11·0.93·1.02로 n과 무관하게 배회한다.

"오늘 방문한 고유 사용자 수"에 2배 오차가 충분한가 — **충분한 경우**: 대략적 용량 산정이나 추세·이상 탐지("트래픽이 대충 두 배 됐다")처럼 자릿수만 맞으면 되는 대시보드. **아닌 경우**: 고유 사용자당 과금, 정확한 광고 도달 수 보고, SLA/쿼터 판정처럼 150만이냐 230만이냐가 결정을 바꾸는 곳 — 여기선 2배 오차가 그대로 돈·계약 오류가 된다.

## Task 3 · 같은 메모리, 더 적은 실수

바꾼 파라미터는 **해시 개수 k**다. §4.4.2의 FP율 `(1 - e^(-kn/m))^k`를 k로 미분해 0으로 두면 최소가 `k* = (m/n)·ln2`에서 나온다. 이 과제는 m=80,000 bits, n=8,000 items로 `m/n=10`이 고정이라 `k* = 10·ln2 = 6.93 → k=7`. Naive는 k=1이라 비트를 낭비했고, k=7로 바꾸니 FP율이 9.511% → **0.831%** (91.3% 감소), 거짓 음성 0, 예산 내(80,000 bits).

R6 — 10 bits/item의 이론 바닥은 `k=7`일 때 `(1 - e^(-0.7))^7 ≈ 0.82%`이고, 실측 0.831%로 사실상 바닥에 도달했다(약 0.01%p 차이는 유한 표본 오차).

n을 모를 때 — 너무 낮게 잡으면 실제 아이템이 예상보다 많이 들어와 비트가 포화되고 FP율이 급격히 치솟는다(최악엔 거의 모든 조회가 "yes"). 너무 높게 잡으면 k가 과해지거나 비트당 아이템이 적어져 메모리를 낭비한다. 실무 해법은 **확장형(scalable) Bloom filter** — 채워지면 새 필터를 이어 붙여 목표 FP율을 유지 — 또는 삭제까지 되는 Cuckoo filter를 쓰는 것이다.
