## Task 1 — Minhash & LSH

특성 행렬을 행 단위로 **딱 한 번만** 훑어 시그니처를 만드는 one-pass 알고리즘(`SIG`를 ∞로 초기화 → 1이 있는 열만 min 갱신)을 구현했다. 행렬이 메모리에 안 들어간다는 전제 때문에 정렬·재스캔 대신 스트리밍 방식을 썼다. 교재 §3.3.5 예제(서명 S1=[1,0], S2=[3,2], S3=[0,0], S4=[1,0])를 그대로 재현해 `python task1_minhash.py --verify`가 `all ok`를 출력한다. S1·S4가 두 해시 모두 일치해 유사도를 1.0으로 과대추정(실제 2/3)하는 것은 해시가 2개뿐이라 그렇고, 해시 수를 늘리면 추정 분산이 줄어드는 대신 계산·저장 비용이 커진다.

## Task 2 — Crossover (내 기계)

Windows 11 · Intel Family 6 Model 142 노트북 CPU · Python 3.13.2에서 측정했다. 실제 크기가 달라지는 250→2,000 구간에서 브루트포스가 이차(2배당 약 3.9배)임을 확인했다. n=4,000·8,000은 브루트 비교수가 2,246,140으로 **동일**했는데, 이는 하니스의 `bench.build()`가 문서를 2,120개만 만들고 `[:n]`이 그 이상을 못 자르기 때문 — 측정 상한이 2,120개라는 뜻이다("숫자가 안 맞으면 측정이 잘못된 것"이라는 A4 포인트). 이 범위에선 LSH가 항상 느렸고(2,000개에서 브루트 16.3초 vs LSH 75.0초), 크로스오버는 외삽하면 **≈9,200개** 부근으로 추정된다. LSH가 작은 n에서 지는 이유는 비교 전에 모든 문서의 시그니처(128 해시)를 먼저 만드는 선형 선투자 비용 때문이다. (자세히: `w03-lsh/out/curve.md`)

## Task 3 — 적게 비교하기

시그니처 길이 n=128을 b=32개 밴드(r=4)로 나눴다. S-곡선의 계단은 `(1/32)^(1/4) ≈ 0.420`으로, 임계값 0.6보다 일부러 낮게 뒀다. 심어둔 쌍의 최소 유사도가 0.622라 `P(0.622)=1-(1-0.622⁴)³²≈0.994`로 거의 다 잡히고, 무관한 쌍(≈0.006)은 `P≈4e-8`로 사실상 후보가 안 된다. 결과는 recall 100%, 비교 126회(2,246,140 대비 **99.99% 회피**)로 strong 등급. 계단을 임계 위로 올리면(b=16, 계단 0.707) recall이 71.9%로 무너지는 것도 실측으로 확인했다. (자세히: `w03-lsh/out/observation.md`)
