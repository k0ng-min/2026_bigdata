# Week 5 · Link Analysis (PageRank) — 관찰 노트

## Task 1 · PageRank와 두 가지 고장

깨진 버전에서 dead end(나가는 링크가 없는 노드)의 rank는 **그냥 증발한다** — 어디로도 분배되지 않아 매 반복마다 총합이 줄고 결국 0으로 고갈된다. 고친 버전에서는 새어나간 그 몫을 **모든 노드에 균등하게 재분배**한다(내가 택한 방법). dead end 를 재귀적으로 제거하는 §5.1.3 방식도 defensible하지만, 균등 재분배가 한 줄로 끝나고 spider trap 까지 같이 고친다.

같은 한 줄(텔레포트)이 두 고장을 모두 고치는 이유: dead end 는 "rank 가 빠져나가 못 돌아오는" 문제, spider trap 은 "rank 가 갇혀 못 빠져나오는" 문제인데, 텔레포트는 **어느 노드에서든 모든 노드로 가는 보장된 통로**를 매 반복 더해준다. 빠져나갈 길과 돌아올 길을 동시에 뚫으므로 두 문제가 같은 수단으로 사라진다.

beta 는 물리적으로 **서퍼가 링크를 따라갈 확률**이다. 확률 `1 - beta`로는 링크를 무시하고 균일하게 고른 임의의 페이지로 **텔레포트**한다(지루해져서 새 URL 을 치는 행동).

## Task 2 · 수렴 비용 (내 기계 측정)

측정 기계는 Windows 11 · Intel Family 6 Model 142 · Python 3.13.2다. beta → 1 로 갈수록 반복 수가 단조 증가했다(0.5→14, 0.7→17, 0.85→20, 0.95→23, 0.99→24회). 반복마다 오차가 대략 beta 배(구글 행렬의 둘째 고유값 ≈ beta)씩 줄어드는데, beta 가 1 에 가까우면 한 번에 줄어드는 양이 작아 같은 tol 에 닿는 데 더 오래 걸리기 때문이다(극한 beta=1 은 텔레포트 없는 깨진 버전이라 수렴 보장 안 됨).

A4 — 그래프를 1,200 → 6,000 노드로 5배 키우면 **반복 수는 거의 그대로(20→22)**지만 **벽시계 시간은 약 5배(0.048→0.224s)** 늘었다. 반복 수는 수렴 속도라는 수학적 성질이고, 시간은 반복 한 번의 비용(엣지 수 비례)×반복 수라는 작업량이라서 서로 다르게 움직인다.

A6 — top-10 **집합은 모든 beta에서 동일**했고, beta 0.70부터 7·8위(`p00000`↔`p00004`)만 자리를 바꿨다. 즉 상위 순위는 beta 선택에 견고하므로, 공개된 랭킹의 상위권은 0.85 라는 관행적 선택에 흔들리지 않는다고 믿어도 된다(흔들리는 건 리스트 깊은 곳의 근소한 동률뿐).

## Task 3 · 행렬로 안 들어가는 그래프

M(전이 행렬)을 만들지 않고, 이미 주어진 **인접 리스트**와 rank 벡터 두 개(`r`, `nr`)만 든다 = **2n floats**. dense 는 n² floats(1200노드 → 144만)를 쓰는데, 여기선 2n(2,400)뿐이라 **600배 적은 메모리, 66배 빠른 속도**로 dense 와 1e-15 이내 동일한 답을 낸다.

R5 — 텔레포트 항은 모든 노드에 `(1-beta)/n`을 더하므로 밀집 연산처럼 보이지만, 이는 **모든 노드에 같은 상수 하나를 더하는 것**이라 스칼라를 한 번 계산해 브로드캐스트하면 끝이다(O(n), n×n 행렬 불필요). dead end 재분배도 `beta·(dead rank 합)/n`이라는 똑같은 모양의 상수 하나라서 마찬가지다. 밀집으로 보이는 두 항이 사실은 스칼라 하나씩이다.

노드별 최대 오차는 **1.18e-15**로, 이는 버그가 아니라 dense 와 합산 순서가 달라 생기는 부동소수점 반올림 차이다.
